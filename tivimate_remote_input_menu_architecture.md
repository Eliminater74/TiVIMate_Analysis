# TiViMate Remote Input & Menu Customization Architecture — Reference Analysis

This document provides a highly detailed architectural analysis of **TiViMate's remote control (D-pad) key mapping and menu editing engines**. It details how the app captures hardware remote clicks, distinguishes long-press events, overrides standard Android view-local focus paths, and structures dynamic layout customizations for bottom and sidebar quick menus.

---

## 1. D-PAD / REMOTE KEY INPUT & ACTION INTERCEPTION SYSTEM

### I. User-Flow Level Behavior
*   **Context-Sensitive Hotkeys**: Tapping a button triggers different behaviors depending on what is currently showing on screen. For example, pressing D-pad Left while watching a video changes channels, but pressing it in the EPG grid shifts the time slider.
*   **Long-Press Action Sets**: Long-pressing D-pad Center opens the Quick Actions Overlay; long-pressing D-pad Down displays the Recent Channels list; long-pressing Back closes active menus instantly.
*   **Full Remote Remapping**: A dedicated settings screen lets the user map specific actions to keys (e.g., mapping yellow/blue color buttons or custom play/pause keys to target triggers).

### II. Architecture Pattern
*   **Window-Callback Key Dispatcher**: Rather than attaching individual key listeners to every child view (which creates focus chaos), TiViMate intercepts key inputs at the highest level—the window callback lifecycle (`MainActivity.dispatchKeyEvent`).
*   **Stateful Key-Action Router**: Intercepted keys are passed to a central router. The router checks the active UI state (e.g., EPG_VISIBLE, PLAYER_ONLY, MENU_OPEN) and resolves the key to an action mapped in user settings.

```
[ Hardware Remote Key Click ] 
           │
           ▼
[ MainActivity.dispatchKeyEvent() ]
           │
           ▼
[ High-Level Action Router ] ◄─── Reads State ─── [ Active UI State Manager ]
           │
           ├─► State: PLAYER_ONLY ──► Map key directly to PlayerActions
           ├─► State: EPG_VISIBLE   ──► Forward to Custom EPG focus controller
           └─► State: OVERLAY_OPEN  ──► Consume key in Overlay View Group
```

### III. Key Classes, Files & Resources Observed
*   **`sources/p363/LayoutInflaterFactory2C4430.java`** & **`sources/p151/AbstractActivityC2438.java`**: The core window lifecycle dispatcher wrappers that capture raw key events.
*   **`KeyEvent.getRepeatCount()` & `KeyEvent.isLongPress()`**: Native frameworks used to catch long-press events.
*   **`ar.tvplayer.tv.R.attr.u_res_0x7f0404ad`**: Attribute binding definitions representing remappable key indexes.

### IV. Important Constants & Settings Strings
*   `"Long press"` / `"Short press"` string preferences mapped to specific integer action IDs.
*   `KEYCODE_DPAD_CENTER`, `KEYCODE_BACK`, `KEYCODE_BUTTON_1` (color buttons).

### V. Performance or UX Reason This Matters
*   **Focus Loop Block**: Standard Android focus traversal is highly fragile on Android TV, often getting stuck in layout edges or "focus traps." Decoupling raw input from view layouts guarantees that focus changes are absolute and predictive.

### VI. What PureFusionIPTV Should Adopt Conceptually
*   **Unified Window Dispatcher**: Implement a high-level `dispatchKeyEvent` override inside your base activity. Intercept keys globally and map them to custom action interfaces depending on which layout wrapper is active:
    ```kotlin
    override fun dispatchKeyEvent(event: KeyEvent): Boolean {
        val actionType = if (event.repeatCount > 0) ActionType.LONG else ActionType.SHORT
        if (event.action == KeyEvent.ACTION_DOWN) {
            if (actionRouter.routeKey(event.keyCode, actionType)) {
                return true // Input consumed
            }
        }
        return super.dispatchKeyEvent(event)
    }
    ```

### VII. What PureFusionIPTV Should Avoid
*   **Nested View OnKeyListeners**: Avoid attaching isolated `OnKeyListener` blocks directly inside RecyclerView viewholders. This results in event-propagation leaks and focus stutter.

### VIII. Risk Level
*   **Medium**. Focus conflicts are easy to introduce when multiple overlay cards are open.

### IX. Suggested PureFusion Beta 10 Phase
*   **Phase 1** (Core remote action architecture).

### X. No-Code-Copy Warning
*   **Warning**: Do not copy decompiled key event wrappers or event loop maps from `LayoutInflaterFactory2C4430.java`. These represent obfuscated classes generated by R8 when packaging app callback factories.

## 2. MENU EDITING & QUICK ACTION CUSTOMIZATION

### I. User-Flow Level Behavior
*   **Quick Menu Customization**: Users can toggle which buttons (e.g. Subtitles, Audio, PiP, Sleep Timer) are visible in their bottom actions overlay.
*   **Reordering Buttons**: Users can slide buttons left/right to change their order in the overlay panel.
*   **Restore Defaults**: A single button restores the layout to factory settings.

### II. Architecture Pattern
*   **Action Bitmask Configurator**: Each menu item is assigned a static ID. The list of active, ordered menu actions is stored in SharedPreferences as a serialized integer array or comma-separated string (e.g., `5,1,12,3`).
*   **Dynamic Item Inflator**: When the Quick Actions card is opened, the view reads the list string from preferences, filters out disabled actions, and dynamically inflates item elements into a horizontal grid container.

### III. Key Classes, Files & Resources Observed
*   **`sources/p312/C3860.java`** (The OSD overlay control view renderer):
    *   Binds drawable resource parameters based on dynamic preferences.
    *   Resolves R layout definitions dynamically using style resource indices.

### IV. Important Constants & Settings Strings
*   `"u_res_0x7f13009e"`, `"u_res_0x7f1300bf"` (localized strings for subtitle and audio labels).
*   `"visible_quick_actions"` configuration strings.

### V. Performance or UX Reason This Matters
*   **Customization Flexibility**: IPTV viewers are highly opinionated about remote control layouts. Giving them control over menu items reduces click counts and improves visual clarity.

### VI. What PureFusionIPTV Should Adopt Conceptually
*   **Serializable Action Lists**: Define your actions as an Enum. Save the user's active layout as a serialized JSON list inside your preferences database:
    ```kotlin
    enum class MenuAction { PLAY_PAUSE, ASPECT_RATIO, SUBTITLES, AUDIO_TRACK, RECALL }
    // Save as: ["PLAY_PAUSE", "SUBTITLES", "AUDIO_TRACK"]
    ```
    During view inflation, loop through this list to dynamically add cards into your horizontal control grid layout.

### VII. What PureFusionIPTV Should Avoid
*   **Hardcoded Menu Layouts**: Avoid setting up fixed, static XML buttons for TV controls. This prevents you from supporting user customization or adding new settings indicators in the future.

### VIII. Risk Level
*   **Low**.

### IX. Suggested PureFusion Beta 10 Phase
*   **Phase 2** (UI custom menus).

### X. No-Code-Copy Warning
*   **Warning**: Do not copy any custom adapters or resource arrays from `p312.C3860`. These are heavily obfuscated view-bindings with hardcoded layout indexes.

## PureFusionIPTV Beta 10 Recommendations

### Low-Risk Actions
*   Define a global `DpadAction` Enum inside your common core module.
*   Add a shared preference setting for long-press durations (defaulting to 500ms).

### Medium-Risk Actions
*   Implement a master `WindowCallback` key dispatcher in `MainActivity` to intercept remote color buttons and map them to direct player actions (recall, mute, search).

### High-Risk Actions
*   Overriding long-press actions for keys that have system-level locks (like the TV's home or source buttons, which vary across manufacturer frameworks and can cause firmware crashes).

### What to Measure First
*   Benchmark remote click processing times. Input routing should take **less than 1ms** from the hardware interrupt to the action dispatch.

### What Not to Copy Directly
*   Do not copy key indices or action maps from the decompiled `p363` callbacks.

### Suggested Implementation Phase
*   **Beta 10 Core Focus**: Remote input mapping must take absolute priority to ensure a highly responsive, high-end "couch UX."
